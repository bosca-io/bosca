# Bosca KMP

This component contains shared client code (`auth-shared`, `client-core`, `dom-shared`, and
`bible-dom-shared`) plus analytics runtime and compiler tooling. Its modules belong to the
workspace's root Gradle build. Dependency versions are in
[gradle/libs.versions.toml](../gradle/libs.versions.toml).

Run Gradle from the workspace root:

```bash
./gradlew :bosca-kmp:test
./gradlew :bosca-kmp:auth-shared:compileKotlinJvm
```

The CocoaPods specs under KMP modules are generated by Gradle. From the workspace root, run
`./gradlew :bosca-kmp:auth-shared:podspec :bosca-kmp:client-core:podspec :bosca-kmp:analytics-core:podspec`
before installing Pods for an iOS consumer.

## GraphQL client identity

Initialize client-core with the stable application ID before resolving the shared GraphQL client:

```kotlin
Providers.initialize("my-app", AppProviderRegistrar())
```

The client sends `X-Installation-ID`, `X-App-ID`, and `X-App-Version` on every query, mutation, and upload once
the installation provider is registered. Android and iOS read the installed package version. Desktop applications
pass their packaged version with `-Dbosca.app.version=...`; unpackaged desktop and web development runs report
`dev`. When analytics is registered, requests also include `X-BA-Session-ID`, read from the current
analytics session for each request.

## Analytics

`analytics-core` is the portable Bosca analytics runtime for Android, iOS, and desktop. It contains:

- the event model, factories, interceptors, and DI-provided `AnalyticsService`;
- the Bosca collector sink with Room-backed offline batching, retries, installation identity, device context, sessions, and heartbeats;
- generated GraphQL feature-flag evaluation and subscriptions, with Room-backed cache hydration, typed accessors, and change observation;
- Compose screen, Navigation 3, control, input, visibility, scroll, and unhandled-exception instrumentation;
- annotations and scoped context consumed by `analytics-compiler`.

The runtime is organized by responsibility: public event models and services live in `bosca.analytics.api`, automatic tracking in `bosca.analytics.instrumentation` and `bosca.analytics.compose`, collector delivery in `bosca.analytics.delivery`, structured storage in `bosca.analytics.persistence`, Room adapters in `bosca.analytics.persistence.room`, and feature flags in `bosca.analytics.experimentation`.

Browser DOM tracking, Nuxt, and Vue integration stay in the TypeScript package. On native targets, the compiler plugin is the auto-instrumentation boundary.

### Add the compiler plugin

The `io.bosca.analytics` Gradle plugin adds `io.bosca:analytics-core` to JVM or KMP projects and loads the K2 compiler plugin for every Kotlin compilation.

```kotlin
plugins {
    kotlin("multiplatform")
    id("io.bosca.analytics") version "<bosca-version>"
}

analytics {
    enabled.set(true)
    verbose.set(false)
}
```

The compiler instruments Compose behavior without requiring annotations:

- Navigation 3 `NavDisplay` back stacks emit destination impressions and `initial`, `push`, `pop`, and `replace` transitions;
- Material and Material 3 buttons, cards, chips, navigation controls, toggles, checkboxes, switches, sliders, and Foundation click/select/toggle callbacks become semantic interaction events;
- `combinedClickable` distinguishes click, long-click, and double-click actions, while three rapid clicks emit a separate rage-click event;
- text fields and search fields emit focus, blur with dwell time, and focused-field abandonment without recording field values;
- horizontal and vertical `ScrollState`, `LazyColumn`, and `LazyRow` usage emits the 25%, 50%, 75%, 90%, and 100% milestones and a maximum-depth event when disposed.

Navigation owns page identity for content rendered by `NavDisplay`; destination functions do not need an `@AnalyticsScreen` annotation. Use `@AutoInstrument` to override the generated element identity and type for a composable subtree or opt that content into dwell-based visibility tracking, and use `@AnalyticsIgnore` to opt a class or function out. These annotations do not create generic function-entry events.

```kotlin
import bosca.analytics.AnalyticsIgnore
import androidx.compose.material3.Button
import androidx.compose.runtime.Composable

@Composable
fun CheckoutScreen() {
    Button(onClick = ::submitOrder) {
        // The callback is wrapped automatically and inherits the Navigation page.
    }
}

@AnalyticsIgnore
@Composable
fun InternalDebugScreen() {
    // No automatic control events are emitted here.
}
```

For Navigation 3, instrumentation attaches directly to `NavDisplay(backStack = ...)`; route tracking does not depend on destination function names. Implement `AnalyticsNavigationRoute` on application route keys to provide stable paths, titles, and safe dimensions:

```kotlin
import bosca.analytics.api.AnalyticsNavigationRoute
import bosca.core.navigation.Route

data class BookRoute(val bookId: String) : Route(), AnalyticsNavigationRoute {
    override val analyticsPath = "/books/$bookId"
    override val analyticsTitle = "Book"
    override val analyticsExtras = mapOf("book_id" to bookId)
}
```

Without that interface, string keys become paths and other keys use a normalized class name (`BookDetailsRoute` becomes `/book-details`). Route object properties are never reflected or serialized automatically.

Use `@AnalyticsScreen` only for a page outside Navigation that needs to establish its own stable identity:

```kotlin
import androidx.compose.runtime.Composable
import bosca.analytics.AnalyticsScreen

@AnalyticsScreen(id = "offline-receipt", path = "/offline-receipt", title = "Receipt")
@Composable
fun OfflineReceiptPage() {
    // This page is not rendered by NavDisplay.
}
```

### Add scoped context

`ProvideAnalyticsContext` adds metadata for automatically instrumented Compose descendants. Nested providers merge their page, element, extras, and content values.

```kotlin
import bosca.analytics.compose.ProvideAnalyticsContext
import bosca.analytics.instrumentation.AnalyticsInstrumentationContext

ProvideAnalyticsContext(
    AnalyticsInstrumentationContext(extras = mapOf("experiment" to "compact-checkout")),
) {
    CheckoutScreen()
}
```

Use `withAnalyticsContext` for structured coroutine work, `analytics.analyticsCoroutineScope()` for an explicitly owned application scope, and `rememberAnalyticsCoroutineScope` for a composition-owned scope. Events and uncaught coroutine failures inherit the scoped context. Cancellation is never reported as an error.

Calling `Analytics.initialize(...)` during application startup installs a chained platform exception handler. Uncaught JVM/Android exceptions and Kotlin/Native unhandled exceptions are persisted as fatal error events and given a bounded best-effort flush before the existing platform handler continues. Configure the limits or disable process-level capture through `BoscaSinkConfig.automaticInstrumentation`.

### Configure event delivery

`analytics-core` is composed through Bosca DI. Register the application's ordinary providers first, then initialize analytics:

```kotlin
import bosca.analytics.Analytics
import bosca.analytics.api.AnalyticsLifecycle
import bosca.analytics.api.AnalyticsElement
import bosca.analytics.experimentation.FeatureFlagOptions
import bosca.core.platform.providers.Providers
import bosca.di.AppProviderRegistrar
import bosca.di.annotation.Provider
import bosca.di.annotation.Providers
import bosca.di.provide

@Providers
class AppAnalyticsProviders {
    @Provider(singleton = true)
    fun featureFlagOptions() = FeatureFlagOptions(
        identity = { currentPrincipalId() },
    )
}

Providers.initialize("my-app", AppProviderRegistrar())
val analytics = Analytics.initialize(appId = "my-app")

val analyticsLifecycle = provide<AnalyticsLifecycle>()
analytics.logImpression(AnalyticsElement(id = "home", type = "screen"))
analytics.logInteraction(AnalyticsElement(id = "save", type = "button"))
```

The app-ID analytics overload appends the collector's `/api/v1` path and reads the installed app version from
Android/iOS package metadata. Desktop applications pass their packaged version with `-Dbosca.app.version=...`;
an unpackaged development run reports `dev`. The analytics provider reads `BoscaAuth.currentUser` for every
event, so the next event automatically reflects sign-in, sign-out, and account switches while queued events keep
the identity captured when they were recorded.

The application registrar name is determined by its `ProviderRegistrarPrefix`; `AppProviderRegistrar` is illustrative. Call `Analytics.initialize(...)` after `Providers.initialize(...)` and before UI creation, then install the returned service at the Compose root. `LocalAnalytics` never performs blocking DI resolution:

```kotlin
ProvideAnalytics(analytics) {
    App()
}
```

Lifecycle operations resolve the DI-owned sink or service instead of constructing their dependencies:

```kotlin
import bosca.analytics.delivery.BoscaSink

val sink = provide<BoscaSink>()
sink.pause()
sink.resume()
analytics.flush()
analyticsLifecycle.close()
```

Queued events and feature-flag snapshots use Room with the bundled SQLite driver on every target. On Android, the Room provider uses client-core's existing `PlatformContexts` application context, so `Analytics.initialize(...)` needs no Android-only setup.

`analytics-core` owns installation registration and the durable `__iid` preference. Its providers bind client-core's `InstallationIdProvider` consumer contract to the Analytics-owned implementation, so device registration, push workflows, event delivery, and experimentation all receive the same identity.

Feature-flag queries and subscriptions use client-core's DI-provided `GraphQLClient` and `GraphQLSubscriptionClient`, including its generated operations and authentication. Analytics does not create another GraphQL transport or handle GraphQL envelopes and WebSocket frames itself. When `AnalyticsLifecycle` is running, the shared GraphQL client's non-sensitive request observer records operation name, duration, and terminal outcome; documents, variables, response data, and URLs are never copied into analytics events.

Room stores `AnalyticsContext` snapshots in their own table and relates individual `AnalyticsEvent` rows to them. Successfully delivered context groups are deleted transactionally, failed groups remain available after a process restart, and a new sink automatically schedules restored events for delivery. The event store API is structured; it never serializes or replaces an entire queue as a string.

### Feature flags

Feature flags are also resolved from Bosca DI. The client automatically receives the Analytics-owned installation identity, Room cache, runtime scope, logger, and client-core GraphQL transports:

```kotlin
import bosca.analytics.experimentation.FeatureFlagClient
import bosca.di.provide

val flags = provide<FeatureFlagClient>()
flags.loadCache()
flags.initialize()
flags.addRealtimeListener()

if (flags.getBoolean("new-library")) {
    // ...
}

flags.close()
```

`identity` is a stable application-level identifier used only to scope the Room cache. Authentication tokens are used only on network requests and are never hashed or persisted as cache keys.

The named analytics `HttpClient` provider (`ANALYTICS_HTTP_CLIENT`) is reserved for collector event delivery and installation registration. GraphQL transport remains owned by client-core.

Every KMP collector event request includes `X-Installation-ID`, `X-App-ID`,
`X-App-Version`, and `X-BA-Session-ID`. Queued events retain the session ID captured when they were recorded.
The initial installation-registration request includes the application headers;
the installation header begins with the first request after the collector has issued that ID.
