# Kit Configuration

The standard [Helm](/kit-reference/kubernetes#standard-helm-deployment) and [Swarm](/kit-reference/swarm#standard-swarm-deployment) installations generate Kit's runtime configuration. Select a harness, supply its provider credential, and use the platform's normal deployment process. The settings below explain those defaults and their optional overrides.

| Layer | Owner | Contents |
| --- | --- | --- |
| Deployment `kit.harness` section | Generated by Helm or the Swarm installer; custom installations can supply it directly | Available runtime profiles, infrastructure, image identity, endpoints, scope ceilings, limits, and approved executable/secret names. |
| Optional private Bosca Configuration named `kit.harness` | Authorized platform administrators | Override the default profile, allowed profiles, Agent defaults, approved model choices, and delegation policy. Group permissions govern conversation overrides. |
| Agent and conversation | Agent administrators and authorized conversation owner | Instructions, managed context, selected sources, and permitted conversation overrides. |

Without a private policy, Kit uses the first configured deployment profile with managed settings. It does not grant users permission to select different profiles or model settings. Create the optional private policy when you need those controls. The application configuration and private policy have different shapes: infrastructure settings deploy runtimes; policy controls which approved choices people may use.

Standard deployment scopes cover permitted content, images, memories, analytics, scripts, pipelines, and Git reads. They include write and execution operations. They do not grant group membership or bypass document/domain permissions. Use `global.kit.profile.scopes` in Helm or the site's `kit.scopes` in Swarm to narrow this ceiling, for example for a read-only deployment.

## Define custom deployment profiles

Merge a section like this into the application configuration used by **both API and Runner**. It is a fragment, not a replacement for their complete database, storage, security, and queue configuration. Replace identity placeholders with values from the qualified image and target cluster.

```yaml
kit:
  harness:
    maxRuntimes: 10
    maxRuntimesPerPrincipal: 2
    maxArchiveBytesPerPrincipal: 68719476736
    profiles:
      - profile: kit-codex
        infrastructure: KUBERNETES
        image: "ghcr.io/bosca-io/bosca/kit-codex-runtime@sha256:QUALIFIED_DIGEST"
        imageId: "IMAGE_CONFIGURATION_DIGEST"
        versions:
          cli: "QUALIFIED_CLI_VERSION"
          adapter: "2.2.2"
          harness: "0.160.1"
          statePolicy: "codex-home-v1"
          transport: 1
          acp: 1
          archive: 1
        endpointTemplate: "http://{job}.{namespace}.svc:8080"
        boscaEndpoint: "https://api.example.com/graphql"
        authenticationMethod: api-key
        idleSeconds: 900
        startupSeconds: 900
        hardRuntimeSeconds: 86400
        credentialLifetimeSeconds: 86400
        scopes: ["content:view", "search:read"]
```

To route the runtime's outbound traffic through the Kit egress proxy, add `egressProxy` (an `http://host:port` origin reachable from the workload) and `egressHosts` (the provider API, such as `api.openai.com` for Codex or `api.anthropic.com` for Claude). See [Outbound destinations](#outbound-destinations).

This example grants a small tool scope ceiling. Add the specific domain scopes needed for writes or execution rather than copying a broad grant. The initiating caller's scopes and groups can narrow it further. Entity ACLs and domain role checks still apply.

The Kubernetes `profile` must match a JobProfile. Swarm uses the same name in its manager controller profiles, `infrastructure: SWARM`, an endpoint with `{service}`, and the running task's pinned digest as `imageId`. See the respective [Kubernetes](/kit-reference/kubernetes) and [Swarm](/kit-reference/swarm) guides.

### Versions and images

The current image descriptors pin these native packages:

| Family | ACP adapter | Native harness/package | State policy |
| --- | --- | --- | --- |
| Codex | `@agentclientprotocol/codex-acp` 2.2.2 | `@openai/codex` 0.160.1 | `codex-home-v1` |
| Claude | `@agentclientprotocol/claude-agent-acp` 0.94.0 | `@anthropic-ai/claude-agent-sdk` 0.3.303 | `claude-home-v1` |

These are the repository's compatibility pins, not a statement about the vendors' latest versions or account entitlements. Build records supply the CLI version and image digest. Claude uses its own image and `authenticationMethod: null`; the pinned adapter reads unattended provider credentials from its environment.

Published deployments bundle the pull reference, image configuration digest, and image-owned component metadata. Kubernetes observations can use the pinned manifest digest or configuration digest. The supervisor separately checks installed package, CLI, protocol, path, and state-policy versions. An identity mismatch stops readiness before native work or archive restore.

## Override the managed policy

Create a non-public Configuration with key `kit.harness` through Studio's configuration administration. Its value starts with:

```json
{
  "defaultProfile": "kit-codex",
  "allowedProfiles": ["kit-codex"],
  "agentDefaults": {}
}
```

Every referenced profile must exist in deployment configuration. Assign group permissions deliberately. `EXECUTE` permits custom harness choices; managed-default use does not itself require that override permission. Administration and configuration edits use the existing configuration access rules.

An Agent-key default can select an allowed profile through `agentDefaults`. The conversation's saved choice is used only while its policy revision, access, and selected profile remain valid. Revoked choices fall back to managed defaults with a notice.

### Model and reasoning policy

Add a `models` entry only when you want managed controls. Use values actually advertised by the deployed harness and approved for the provider account:

```json
{
  "defaultProfile": "kit-codex",
  "allowedProfiles": ["kit-codex"],
  "models": {
    "kit-codex": {
      "defaults": { "model": "APPROVED_ADVERTISED_MODEL_ID", "reasoning": "medium" },
      "allowedModels": ["APPROVED_ADVERTISED_MODEL_ID"],
      "allowedReasoning": ["medium", "high"]
    }
  }
}
```

Each managed control needs an approved default. Resolution is authorized conversation choice, Agent-key default, system default, then harness default for an unmanaged control. Omitting `models` leaves control with the harness and exposes no overrides. Model discovery is not a billing or entitlement service.

### Delegation policy

Delegation is disabled unless the private policy includes `delegation`. Add `ai:delegate` to participating deployment scope ceilings and approve child profiles explicitly:

```json
{
  "defaultProfile": "kit-codex",
  "allowedProfiles": ["kit-codex", "kit-claude"],
  "delegation": {
    "profiles": ["kit-claude"],
    "maxDepth": 1,
    "maxActive": 1,
    "maxChildren": 4,
    "maxRuntimeSeconds": 600,
    "totalRuntimeSeconds": 1800
  }
}
```

Both profiles must also exist in deployment configuration. These limits reserve runtime resources across one parent turn's tree; they do not cap provider tokens or money. See [managed child tasks](/kit-reference/using-kit#managed-child-tasks).

### Outbound destinations

A profile with `egressProxy` sends the runtime's outbound HTTPS through the Kit egress proxy. The proxy opens a destination only when it is approved for that runtime's current generation:

- the profile's `egressHosts`, which name the harness's model provider API;
- the remote MCP registrations resolved for the conversation's agent;
- the administrator's `egressHosts` in this policy, which apply to every profile.

```json
{
  "defaultProfile": "kit-codex",
  "allowedProfiles": ["kit-codex"],
  "egressHosts": ["tools.example.com", "files.example.com:8443"]
}
```

Each entry is a host name with an optional port; the port defaults to 443. Wildcards and IPv6 literals are rejected, and an invalid entry makes the policy invalid. The proxy reads the list on each lookup, so an edit applies to running conversations within its 30-second cache. It doesn't change the policy revision or reset approved conversation choices. The proxy refuses any approved host that resolves to a private, loopback or link-local address.

## Capacity, time, and storage settings

| Setting | Default | Meaning |
| --- | --- | --- |
| `maxRuntimes` / `maxRuntimesPerPrincipal` | 10 / 2 | Admission slots across profiles. Waiting, warm, approval-waiting, and removing workloads consume slots. |
| `maxArchiveBytesPerPrincipal` | 64 GiB | Current, reserved, and pending-deletion archive bytes per principal. A replacement can need room for old and new archives together. |
| `idleSeconds` | 900 | Idle time before normal archival. Reading status does not extend it. |
| `startupSeconds` | 900 | Total activation budget from durable dispatch, including queue waits, restore, and setup retries. |
| `connectionSeconds` | 10 | One control request or ACP connection budget. |
| `readinessSeconds` / `restoreSeconds` | 600 / 600 | Per-attempt setup and restore budgets, within the total startup deadline during activation. |
| `promptSeconds` / `approvalSeconds` | 86,400 / 86,400 | Durable prompt and native permission-decision lifetimes. Approval waits consume prompt time. |
| `cancellationSeconds` | 30 | Grace for confirming cancellation before forced generation retirement. |
| `hardRuntimeSeconds` / `credentialLifetimeSeconds` | 86,400 / 86,400 | Maximum generation and scoped-credential lifetimes. Hard runtime cannot exceed credential lifetime; startup must be shorter than credential lifetime. |
| `archiveSeconds` | 600 | Archive creation, transfer, verification, and commitment attempt. |
| `maxArchiveBytes` | 8 GiB | Individual compressed archive bound. |
| `maxArchiveAgeSeconds` | Unset | Optional cold-state expiry. Unset preserves the checkpoint until conversation deletion. |
| `maxJournalBytes` / `maxJournalTurns` | 64 MiB / 256 | Per-generation receipt and accepted-turn limits. Normal retirement starts between turns at half the byte budget or the turn-count limit. |
| `contextCharacters` | 32,000 | Initial-context budget in UTF-16 code units, not a model token estimate. Supported range: 4,096–131,072. |

Workload CPU, RAM, and writable-storage limits belong to the JobProfile or ServiceSpec. The Swarm profile also supplies its PID limit. Admission counts are not a substitute for those resource bounds. A long approval wait can retain an entire workload; set timeouts and capacity together.

Profiles reject general administrative `:manage`/`:admin` scopes and `ai:execute`/`mcp:execute`. `scripts:manage` is an explicit supported exception; script ACLs still apply. Pipeline authoring also retains its administrator checks. A scope alone does not grant a role or entity permission.

## Apply changes through the lifecycle

Keep API and Runner deployment configuration matched. Policy, source, profile, and integration changes can drain a generation or invalidate native context. Warm runtimes retain prepared tool credentials until retired. After repairing an optional integration or rotating its mounted credential, use **Archive session** while idle and **Resume session**, or **Retry session** for a repaired failure.

An image or harness upgrade also needs archive compatibility review and target qualification. Read [Operations and Support](/kit-reference/operations) before rolling out changes to active sessions.
